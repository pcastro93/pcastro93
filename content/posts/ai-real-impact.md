As misconceptions about AI's impact on Software Engineering continue to grow, I realized that we, as software engineers, might share some of the blame. We often struggle to explain what we do in simple terms to non-technical people. Here is a look at what Software Engineering truly is and how AI actually might help us be better engineers.

### The Real Job

> "Software Engineering is programming integrated over time." - [Titus Winters](https://www.linkedin.com/in/tituswinters)

Software Engineering is much more than writing code. In fact, a recognized best practice is to delay writing code as long as possible. Jumping straight into code often leads to problems like the [Golden Hammer](https://en.wikipedia.org/wiki/Law_of_the_instrument) — treating every problem like a nail just because you have a hammer.

You might not even need any code to solve a problem. Indeed, there might be no problem at all. As [Dave Cheney](https://www.linkedin.com/in/turboencabulator/) points out: "You're not paid to program. You're not even paid to maintain somebody else's program, really. Essentially, you're paid to deliver solutions for the business that you work for." Software Engineering involves [multiple stages](https://en.wikipedia.org/wiki/Software_engineering#Workload) and only one of them focuses heavily on writing code. So, while LLMs excel at that single stage by translating ideas into syntax, it takes a software engineer's technical fluency to drive the system design and problem-scoping that tells the LLM what to translate.

### Upgrading the Instruments, Keeping the Pilot

> "AI is just a tool" — [Grady Booch](http://www.youtube.com/watch?v=AdTICbCjszk&t=1693) and [Linus Torvalds](https://www.youtube.com/watch?v=mfv0V1SxbNA&t=2043s).

For years, engineers have been trying different approaches to minimize writing tedious code. We have seen success in areas like boilerplate code generation, using macros in certain languages, and generating code from specifications. As AI has improved, we've been able to enhance autocomplete tools, and with LLMs we can generate code from natural language.

AI models can be valuable tools across the software development lifecycle, including generating code, [understanding a codebase](https://www.youtube.com/watch?v=CQmI4XKTa0U&t=2763s), learning new technologies, spotting inconsistencies and finding information.

This means that software engineers are now able to focus on more critical parts of their jobs. Instead of spending hours wrestling with syntax and frameworks, they can focus on code quality, best practices, and security. However, having the capability doesn't guarantee results. Simply having this tool won't automatically make us better engineers. We'll still have to know how, when, and where to use the tool. A pilot doesn't become a better pilot simply by having an autopilot system in their airplane. Similarly, we still need to be able to write and understand code manually, without assistance.

### The Reality of the "New Era"

> "I don't think AI is going to wipe out software development, I think it will change it ... but the core skills are still there" — [Martin Fowler](https://www.youtube.com/watch?v=CQmI4XKTa0U&t=6049s)

I have read and heard many claims about how AI will change Software Engineering. Some say [Software Engineering jobs might be automated in the next few months](https://www.youtube.com/watch?v=02YLwsCKUww&t=112s). Yet the same companies building those models, like OpenAI and Anthropic, are hiring software engineers [at unprecedented rates](https://x.com/AznWeng/status/2027035871392698799). In reality, many companies have found that replacing engineers with AI [hasn't worked out](https://www.youtube.com/watch?v=WfjGZCuxl-U). If you have managed to successfully do it, it's likely because you didn't need a software engineer in the first place.

Being in a new era of Software Engineering, as [Grady Booch suggests](https://www.youtube.com/watch?v=OfMAtaocvJw&t=2824s), doesn't imply that we won't need software engineers. Instead, it might be quite the opposite: we might need even more. In this new era, we'll still need to know best practices, identify design flaws and prevent security breaches. We might be able to learn quicker, explore multiple approaches to a single problem, write more robust code, build prototypes rapidly, and do much more. Yet, we will still need to engineer our software.
